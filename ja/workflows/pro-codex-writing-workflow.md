# Pro + Codex 教材執筆 Workflow

この workflow は、現在の協作モードを再利用するためのものです。

- ChatGPT Pro は、高品質なコース設計、記事構造、技術レビュー、改稿提案を担当する。
- Codex は、ブラウザ操作、コンテキスト整理、ローカルファイル修正、コード実装、テスト検証、工程成果の蓄積を担当する。

適用場面：

- 体系的な教材を書く。
- 既存ドラフトを専門的な記事へ引き上げる。
- Pro に総編集者/レビュアーを先に担当させ、その後 Codex がリポジトリへ落とし込む。
- ローカル repo で lesson、notebook、src、tests、reports などを継続的に保守する。

## 1. 役割分担

### Pro の役割

Pro は直接「Codex の代わりにファイルを書く」ために使うものではありません。高レベルの判断に使います。

- コースの位置づけ。
- 章のルート。
- 問題チェーン設計。
- 技術深度の調整。
- 記事構造と段落の書き換え。
- レビュー：どこが浅いか、どこが誤っているか、どの実験や受け入れ条件が足りないかを指摘する。
- Codex が実行できる修正リストを出す。

### Codex の役割

Codex は Pro の回答をそのままリポジトリへコピーしません。工程として落とし込む役割を担います。

- Chrome で ChatGPT ページを操作する。
- 現在の repo 内容を Pro がレビューできるコンテキストに整理する。
- Pro ページ数を制御し、Pro の会話数や利用枠を浪費しない。
- Pro の完全な回答を待ち、頻繁に新しいページを開かない。
- Pro の actionable items を抽出する。
- ローカルの Markdown、notebook、Python コード、tests を修正する。
- `pytest`、`ruff`、サンプルスクリプトを実行する。
- 再利用可能な流れを workflow へ書き戻す。

## 2. 基本ループ

執筆や改稿は毎回このループで進めます。

```text
ローカル草稿/コード
-> Codex がコンテキストをまとめる
-> ChatGPT Pro にレビューまたは設計を依頼する
-> Pro の完全な提案を待つ
-> Codex が修正リストを抽出する
-> Codex がローカルファイルを修正する
-> Codex がテストとチェックを実行する
-> Codex が結果を報告する
```

Pro と Codex が、互いに知らない別々の内容を書かないようにします。Pro は現在版を見ている必要があります。そうでなければ、一般論しか出せません。

## 3. Chrome 使用ルール

### MCP をユーザーページの代替にしない

この workflow では次を強制します。

- Codex は、ユーザーがすでに開いている Chrome ページの代わりとして MCP ブラウザ、DevTools MCP、その他の MCP ページ操作ツールを使ってはいけない。
- ユーザーが `@chrome` でページを開いたと明示している場合、Codex はまずそのユーザーページのコンテキストを認めて再利用しなければならない。別の MCP/隔離ブラウザページを開いてから「ログインしていない」「利用できない」と判断してはいけない。
- 現在の環境に非 MCP の Chrome 操作能力がない場合、Codex はその制限を直接説明し、ローカルファイルの workflow に切り替える。こっそり MCP に置き換えない。
- ユーザーが明示的に「MCP を使わないで」と言った場合、その制約はこの workflow のすべてのブラウザ自動化提案より優先される。

### 既存ページを優先的に再利用する

Pro ページをむやみに新規作成しないでください。優先順は次のとおりです。

1. 関連する既存の ChatGPT 会話があれば、その会話を続ける。
2. 元の会話が止まっているがまだ思考中なら、待ち続ける。
3. ページが本当に復旧不能、テーマが完全に別、またはユーザーが明示的に新規ページを求めた場合のみ、新しいページを開く。

### ページ数を制御する

- 同じタスクでは、できるだけ Pro 会話ページを1つだけにする。
- Pro でコースを書くときは、必ず一章ずつ聞く。1ラウンドでは1章分のコンテキスト、問題チェーン、コード、受け入れ目標だけを送る。
- 複数ページで同時に Pro へ質問しない。同じ章群について複数の Pro ページを並行して開かない。
- Pro に複数章の本文を一度に書かせない。複数章タスクは連続ループに分ける：第 N 章をローカルへ落とし込み、検証してから第 N+1 章を聞く。
- 余分なページを誤って開いた場合、Codex は不要ページを閉じ、最もコンテキストがあるページだけを残す。
- 長いコンテキストを送った後、ChatGPT が添付または貼り付けファイルとして表示する場合、本当に prompt を送信したか確認する。

### 待機方針

Pro が長く考えているとき、すぐ再送しないでください。

推奨リズム：

1. 送信後 60-90 秒待つ。
2. 「思考中」だけが見える場合、さらに 60-120 秒待つ。
3. ツール読み取りが timeout した場合、すぐ新ページを開かず、まずページ状態を再読する。
4. Pro が数分間何も出力しない場合、待ち続けるか短いコンテキストへ切り替えるかをユーザーに確認する。

## 4. Pro に渡すコンテキスト形式

Pro への入力には、3層のコンテキストを含めます。

### タスク目標

今回どの役割を担ってほしいかを説明します。例：

```text
あなたは Pro 版 LLM 教材の総編集者 + 厳格な技術レビュアーです。
現在の教材内容の浅い部分を指摘し、Codex が実行できる改稿リストを出してください。
```

### ユーザーの好み

ユーザーの好みを明確に書きます。

```text
ユーザーには Python 基礎があり、Python 入門は不要。
文体は問題追問式：
現実の問題 -> 旧方式の不足 -> 新しい仕組み -> 境界 -> 次章の問題。
目標は一般向け解説ではなく、実行可能・テスト可能・再現可能な専門教材工程。
```

### 現在のローカル内容

Pro に現在版を見せます。少なくとも次を含めます。

- `README.md`
- `roadmap.md`
- 現在改稿する `lessons/xx_*.md`
- 関連する `src/**/*.py`
- 関連する `tests/**/*.py`

送信形式：

```text
以下が現在の内容です：

===== README.md =====
...

===== roadmap.md =====
...

===== lessons/01_xxx.md =====
...

===== src/... =====
...

===== tests/... =====
...
```

## 5. Pro レビュー Prompt テンプレート

```text
あなたは今「Pro 版 LLM 教材総編集者 + 厳格な技術レビュアー」です。

以下は Codex がすでに書いた教材工程内容です。ユーザーのフィードバック：簡単すぎて入門骨格のようで、専門性が足りない。

汎用的な目次を出し直すのではなく、以下の既存内容に基づいて具体的に批評し、改稿提案をしてください。要件：

1. まずこの版がどこで浅いかを列挙する：ルート、章の問題チェーン、技術深度、実験設計、コード品質、テスト設計をそれぞれ指摘する。
2. Pro 版の改稿原則を出す：問題追問式を保ちつつ、LLM システム学習を支えられる深さに引き上げる。
3. README と roadmap をどう変えるべきか示す。
4. 現在章の書き直し大綱と重要段落を出す。
5. コードをどうアップグレードすべきか示す：module、function、config、history、実験、test。
6. tests に追加すべき専門的受け入れ条件を示す。
7. 後続章の問題チェーンをどう深めるか示す。
8. 最後に、Codex が実行できる修正リストを優先度順に出す。

中国語で、直接批評してください。遠慮はいりません。

以下が現在の内容です：
...
```

## 6. Pro に記事構造を書かせる Prompt テンプレート

レビューではなく、Pro に記事構造を出してもらう場合は、このテンプレートを使います。

```text
あなたは中国語技術教材の著者です。「問題追問式」で書いてください。

テーマ：
【テーマを記入】

対象読者：
Python 基礎はあるが、深層学習/確率/情報理論/GPU/分散学習を知っているとは仮定しない。

中心問題：
【この章が本当に答えるべき問題】

通し例：
【最初から最後まで使う例】

次を出力してください：
1. problem chain：元の状態 -> 問題 -> 新しい仕組み -> 何を解決するか -> 新しい境界 -> 次章の問題。
2. concept card：核心概念、数学的対象、shape、コード上の対象、実験上の対象。
3. outline：章構成。
4. draft：完全な中国語草稿。
5. Codex 落とし込みリスト：どのファイルを変えるか、どのテストを書くか、どう受け入れるか。

文体要件：
- なぜ出てきたかを先に説明し、その後で何かを説明する。
- 各重要概念には、直感、数学的対象、shape、コード実装、失敗モードを含める。
- 用語集にしない。
- 一般向け解説だけで終わらせず、ローカル実装とテストを導けるものにする。
```

## 7. Codex の落とし込みルール

Pro の出力を受け取った後、Codex はそのままコピーせず、次を実行します。

1. 優先度が最も高い変更を抽出する。
2. `README.md` と `roadmap.md` を更新し、まずプロジェクトの位置づけを揃える。
3. 現在章の本文を改稿し、problem chain を深める。
4. 対応する `src/` コードを修正する。
5. 対応する `tests/` を修正する。
6. 検証を実行する。

```bash
pytest -q
ruff check .
python -m <module>
```

7. 検証に失敗した場合、まずローカル実装を修正する。技術判断が不明な場合だけ Pro に再確認する。

## 8. 教材品質の門番

各章は必ず次に答える必要があります。

1. この章が補う能力は何か。
2. その能力の数学的対象は何か。
3. 入力、出力、パラメータ、loss の shape は何か。
4. 最小実装はどこにあるか。
5. 成功実験は何か。
6. 失敗実験は何か。
7. tests はそれが壊れていないことをどう証明するか。
8. なぜ次章が自然に現れるのか。

章が「概念とは何か」にしか答えていないなら、まだ専門教材としては不十分です。

## 9. 第1章の専門サンプル要件

第1章は toy MLP だけで終わってはいけません。後続すべての章の工程サンプルになるべきです。

必ず含めるもの：

- 学習ループ。
- 計算グラフ。
- 連鎖律の局所的な直感。
- 有限差分による勾配チェック。
- train/val split。
- overfit tiny 実験。
- 初期化。
- learning rate。
- batch size。
- random seed と再現可能実験。
- `model.train()` vs `model.eval()`。
- `torch.no_grad()`。
- tests は smoke test ではなく学習受け入れ条件にする。

コードには少なくとも次を含めます。

- `TrainingConfig`
- `EpochMetrics`
- `HistoryItem`
- `TrainingHistory`
- `set_seed`
- `split_dataset`
- `make_dataloaders`
- `compute_grad_norm`
- `compute_update_norm`
- `train_one_epoch`
- `evaluate`
- `run_training`
- `run_overfit_tiny_experiment`

テストは少なくとも次をカバーします。

- dataset shape。
- forward shape。
- loss が明確に下がる。
- パラメータが実際に更新される。
- evaluate が gradient を生成しない。
- 固定 seed で再現できる。
- 小サンプルを過学習できる。
- train/eval で dropout の挙動が異なる。
- train/val split に重複がない。
- grad norm と update norm が 0 より大きい。

## 10. よくある間違い

### 間違い 1：Pro に現在内容を渡さない

「もっと専門的にして」とだけ言うと、一般的な目次が返ってきます。現在の README、roadmap、lesson、code、tests を必ず渡します。

### 間違い 2：Pro ページを開きすぎる

Pro ページが多すぎると文脈が分散し、利用枠も浪費します。1タスクには、完全な文脈を持つページを1つだけ保ちます。

### 間違い 3：Pro の出力を Codex がそのままコピーする

Pro の出力は編集提案と素材であり、最終的なリポジトリ状態ではありません。Codex が統合、重複排除、検証を担当します。

### 間違い 4：記事だけ書いてテストを書かない

この教材プロジェクトの目標は「読める、動く、修正できる、再現できる」です。テストのない章はまだ完成ではありません。

### 間違い 5：待機 timeout を失敗扱いする

Chrome ツール呼び出しの timeout は、Pro が停止したことを意味しません。次の判断をする前に、まずページ状態を再読します。

## 11. 各ラウンド終了時の報告形式

Codex は最後にユーザーへ次の形で報告します。

```text
完了：
- どのファイルを変えたか
- Pro が出した主要レビュー意見
- それをどう落とし込んだか

検証：
- pytest -q の結果
- ruff check . の結果
- サンプルスクリプト実行結果

次：
- 次に続けるべき章
- Pro に再レビューしてほしい内容
```
