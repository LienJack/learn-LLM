# GPT Pro 课程总审提示词

把 `all-articles-for-gpt-review.md` 的全文粘贴到 GPT Pro 后，可以使用下面这段提示词。

```markdown
你是一位资深中文技术教材编辑、LLM 工程课程设计师、机器学习教学审稿人。请你审阅下面这套《LLM 从 0 到领域小模型》的 19 篇课程文章合集，并给出系统性的审稿意见和修改建议。

## 课程定位

这不是 API 教程，也不是只讲概念的科普文章。它是一套面向已经会 Python、但未必系统学过深度学习 / LLM 工程的学习者的中文教材。

课程目标是让学习者从最小训练闭环出发，逐步理解：

训练闭环 -> next-token 语言建模 -> Tokenizer / Dataset -> Embedding -> Attention -> Transformer -> Mini GPT -> Hugging Face 工作流 -> SFT -> LoRA / QLoRA -> 领域数据工程 -> RAG -> 蒸馏 -> 评测 -> 安全与模型卡 -> 量化部署 -> 法律 / 医学领域小模型项目 -> 通用领域模型工程模板

本课程的核心主线是：

> 如果要让模型根据上下文生成可靠答案，需要依次补上哪些能力？这些能力又如何被实验、测试和失败案例验证？

## 目标读者

- 会 Python，能读基础 PyTorch 代码。
- 不默认系统学过深度学习、概率建模、信息论、GPU 训练或分布式系统。
- 想从“能跑 demo”进一步走到“能训练、能评测、能部署、能治理”的 LLM 工程学习者。

## 写作风格要求

请按照“问题驱动的技术概念博客 / 教材”标准审稿，而不是按照百科词条或论文风格审稿。

每章应该优先做到：

1. 先解释这个概念为什么出现，再解释它是什么。
2. 从学习者的真实困惑或能力缺口开始。
3. 用一条清晰的问题演化链推进：
   原来是什么情况 -> 出现什么问题 -> 引入什么机制 -> 解决什么 -> 留下什么新问题 -> 引出下一章。
4. 尽量复用贯穿例子，尤其是“合同条款风险识别 / 法律合同审查”，医学问答作为第二个高风险领域案例。
5. 遇到术语时，先用人话翻译，再给技术边界。
6. 不要写成平行定义列表，不要堆名词。
7. 每章都要保留工程感：shape、输入输出、loss、最小实现、实验观察、失败模式、测试验收。
8. 技术表达要诚实：说明适用边界、非目标、常见误解和高风险场景。

## 请重点审查

### A. 总体结构

- 19 章的演化链是否自然？
- 从第 1 章到第 19 章是否有清晰递进，而不是主题并列？
- 哪些章节之间的承接弱，需要补“上一章留下的问题 / 本章解决的问题”？
- 哪些章节顺序、标题或章节职责需要调整？
- 是否存在重复、断裂、跳步、概念提前出现但未解释的问题？

### B. 单章质量

请逐章检查：

- 开头是否从真实问题出发？
- “本章真正要解决的问题”是否足够尖锐？
- “问题链”是否能支撑全文？
- Concept Card 是否有用，还是只是形式化表格？
- 贯穿例子是否一致、具体、可运行？
- 是否有概念解释太抽象、太教材腔、太像定义堆叠的段落？
- 是否有应该补充类比、反例、边界说明或最小例子的地方？
- 结尾是否自然引出下一章？

### C. 初学者可读性

- 哪些段落对目标读者太快、太跳、太术语密集？
- 哪些数学对象、shape、loss 或训练细节需要更平缓地铺垫？
- 哪些地方需要把“工程术语”翻译成更直观的人话？
- 哪些图示、流程图、表格或最小代码片段会显著提升理解？

### D. 工程闭环

请检查每章是否真正回答：

- 当前能力缺口是什么？
- 关键数学对象是什么？
- 输入、输出、参数、loss 的 shape 是什么？
- 最小实现是什么？
- 如何通过实验观察它？
- 常见失败模式是什么？
- tests 如何证明实现没有坏？

如果某章缺少这些要素，请明确指出应补在哪里。

### E. 领域小模型主线

请特别检查“从通用 LLM 基础走向法律 / 医学领域小模型工程”的主线是否足够强：

- 合同风险识别这个贯穿例子是否从第 1 章开始持续发挥作用？
- 法律项目和医学项目是否不仅是附加案例，而是前面能力的综合验证？
- RAG、SFT、LoRA、蒸馏、评测、安全、部署之间的边界是否讲清楚？
- 是否有把 RAG、微调、蒸馏混成一团的风险？
- 高风险领域的拒答、人类审核、证据引用、模型卡和回滚是否讲得足够严肃？

## 输出格式

请不要直接全量重写 19 篇文章。先给“审稿报告 + 修改建议”。

请按以下结构输出：

## 1. 总体判断

用 5-10 句话评价这套文章目前最大的优点、最大风险、最值得优先修改的方向。

## 2. 总体结构修改建议

列出 5-10 条跨章节建议。每条包含：

- 问题
- 为什么影响学习体验
- 建议怎么改
- 影响章节

## 3. 逐章审稿意见

对第 1-19 章逐章给意见。每章请包含：

- 本章作用是否清楚
- 问题链是否成立
- 最需要加强的 1-3 个点
- 建议新增 / 删除 / 移动的内容
- 是否需要补例子、图示、实验、测试或失败模式

## 4. 优先级修改清单

按 P0 / P1 / P2 分级：

- P0：不改会影响整套课程主线或技术正确性
- P1：明显改善学习体验和文章质量
- P2：润色、表达、标题、局部例子优化

## 5. 风格统一建议

请给出一套可复用的单章写作模板，用于后续统一 19 篇文章。模板要符合“问题驱动、概念演化链、贯穿例子、工程闭环”的风格。

## 6. 示例改写

请选择你认为最有代表性的 2-3 个段落，示范如何从“教材式 / 定义式表达”改成“问题驱动、初学者友好、工程边界清楚”的表达。

## 7. 给作者的下一步行动

给出一个实际可执行的修改顺序：先改哪些章，怎么改，每轮修改如何验收。

## 审稿原则

- 技术正确性优先于文采。
- 学习路径清晰优先于覆盖更多概念。
- 不要建议加入过多外部知识，除非它能解决当前文章的断裂或误解。
- 不要把文章改成营销文、公众号爽文或论文综述。
- 保持中文表达自然、清楚、低术语密度，但不要牺牲工程准确性。
- 如果某些内容已经足够好，请明确指出，不要为了给建议而硬挑毛病。
```
