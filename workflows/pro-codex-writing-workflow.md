# Pro + Codex 教材写作 Workflow

这份 workflow 用来复用当前协作模式：

- ChatGPT Pro 负责高质量课程设计、文章结构、技术审稿和改写建议。
- Codex 负责浏览器控制、上下文整理、本地文件修改、代码实现、测试验证和沉淀工程结果。

适用场景：

- 写一套系统教材。
- 把已有草稿升级成专业文章。
- 让 Pro 先做总编辑/审稿人，再由 Codex 落地到仓库。
- 需要在本地 repo 中持续维护 lesson、notebook、src、tests、reports 等内容。

## 1. 分工原则

### Pro 的角色

Pro 不是用来直接“替 Codex 写文件”的，而是用来做高层判断：

- 课程定位。
- 章节路线。
- 问题链设计。
- 技术深度校准。
- 文章结构和段落改写。
- 审稿：指出浅在哪里、错在哪里、缺哪些实验和验收。
- 给 Codex 可执行的修改清单。

### Codex 的角色

Codex 不把 Pro 的回答原样复制进仓库，而是负责工程落地：

- 使用 Chrome 控制 ChatGPT 页面。
- 把当前 repo 内容整理成 Pro 能审稿的上下文。
- 控制 Pro 页面数量，避免浪费 Pro 对话和额度。
- 等待 Pro 完整回答，不频繁新开页面。
- 提取 Pro 的 actionable items。
- 修改本地 Markdown、notebook、Python 代码和 tests。
- 跑 `pytest`、`ruff`、示例脚本。
- 把可复用流程写回 workflow。

## 2. 基本循环

每次写作或改稿都走这个循环：

```text
本地草稿/代码
-> Codex 汇总上下文
-> 发给 ChatGPT Pro 审稿或设计
-> 等 Pro 输出完整建议
-> Codex 提炼修改清单
-> Codex 修改本地文件
-> Codex 运行测试和检查
-> Codex 汇报结果
```

不要让 Pro 和 Codex 同时各写一套互相不知道的内容。Pro 必须看到当前版本，否则它只能给泛泛建议。

## 3. 使用 Chrome 的规则

### 禁止使用 MCP 代替用户页面

本 workflow 强制规定：

- Codex 不使用 MCP 浏览器、DevTools MCP 或其他 MCP 页面控制工具来替代用户已经打开的 Chrome 页面。
- 如果用户明确说已经用 `@chrome` 打开了页面，Codex 必须优先承认并复用该用户页面的上下文，不得自行新开一个 MCP/隔离浏览器页面后判断“未登录”或“不可用”。
- 如果当前环境没有非 MCP 的 Chrome 控制能力，Codex 必须直接说明限制，并改为本地文件流程；不要偷偷换用 MCP。
- 用户明确说“不要用 MCP”时，该约束优先于本 workflow 中所有浏览器自动化建议。

### 优先复用页面

不要随手新开很多 Pro 页面。优先顺序：

1. 如果已有相关 ChatGPT 对话，继续使用原对话。
2. 如果原对话卡住但还在思考，继续等。
3. 只有在页面真正无法恢复、主题完全不同、或用户明确要求新开时，才开新页面。

### 页面数量控制

- 同一任务尽量只保留一个 Pro 对话页。
- 使用 Pro 写课程时必须一章一章问：一轮只提交一个章节的上下文、问题链、代码和验收目标。
- Pro 不能多个页面一起问；不要为同一批章节并行打开多个 Pro 页面。
- 不要一次要求 Pro 同时写多章正文。多章任务必须拆成连续循环：第 N 章完成本地落地和验证后，再问第 N+1 章。
- 如果误开了多余页面，Codex 应关闭无用页面，只保留最有上下文的那一个。
- 长上下文提交后，如果 ChatGPT 显示为附件或粘贴文件，要确认是否真的点了“发送提示”。

### 等待策略

Pro 长思考时不要立刻重发。

建议节奏：

1. 发送后等 60-90 秒。
2. 如果只看到“思考中”，再等 60-120 秒。
3. 如果工具读取超时，先重新读取页面状态，不要马上开新页。
4. 如果 Pro 多分钟无输出，再向用户确认是否继续等或改用精简上下文。

## 4. 给 Pro 的上下文格式

Pro 的输入必须包含三层上下文：

### 任务目标

说明这次要它扮演什么角色，例如：

```text
你是专业版 LLM 教材总主编 + 严格技术审稿人。
请基于当前教材内容，指出哪里浅，并给 Codex 可执行改写清单。
```

### 用户偏好

必须写清楚用户偏好：

```text
用户已有 Python 基础，不需要 Python 入门。
写作风格要求问题追问式：
真实问题 -> 旧方法不足 -> 新机制 -> 边界 -> 下一章问题。
目标不是科普，而是可运行、可测试、可复现的专业教材工程。
```

### 当前本地内容

给 Pro 看到当前版本，至少包括：

- `README.md`
- `roadmap.md`
- 当前要改的 `lessons/xx_*.md`
- 相关 `src/**/*.py`
- 相关 `tests/**/*.py`

发送格式：

```text
下面是当前内容：

===== README.md =====
...

===== roadmap.md =====
...

===== lessons/01_xxx.md =====
...

===== src/... =====
...

===== tests/... =====
...
```

## 5. Pro 审稿 Prompt 模板

```text
你现在是“专业版 LLM 教材总主编 + 严格技术审稿人”。

下面是 Codex 已经写出来的教材工程内容。用户反馈：太简单，像入门骨架，不够专业。

请你不要泛泛重新给目录，而是基于下面现有内容做针对性批改和改写建议。要求：

1. 先列出这版教材浅在哪里：路线、章节问题链、技术深度、实验设计、代码质量、测试设计分别指出。
2. 给出专业版改写原则：保持问题追问式，但提升到能支撑 LLM 系统学习。
3. 给出 README 和 roadmap 应该怎样改。
4. 给出当前章节的重写大纲和关键段落。
5. 给出代码应该怎样升级：模块、函数、config、history、实验、测试。
6. 给出 tests 应该补哪些专业验收。
7. 给出后续章节如何升级问题链。
8. 最后输出一个 Codex 可执行的修改清单，按优先级排序。

请用中文，直接批改，不要客套。

下面是当前内容：
...
```

## 6. 让 Pro 写文章的 Prompt 模板

当不是审稿，而是让 Pro 产出文章结构时，用这个模板：

```text
你是中文技术教材作者，请按“问题追问式”写作。

主题：
【填写主题】

目标读者：
已有 Python 基础，但不假设懂深度学习/概率/信息论/GPU/分布式训练。

核心问题：
【本章真正要回答的问题】

贯穿例子：
【一个从头到尾使用的例子】

请输出：
1. problem chain：原始状态 -> 问题 -> 新机制 -> 解决什么 -> 新边界 -> 下一章问题。
2. concept card：核心概念、数学对象、shape、代码对象、实验对象。
3. outline：章节结构。
4. draft：完整中文草稿。
5. Codex 落地清单：需要改哪些文件、写哪些测试、如何验收。

写作要求：
- 先讲为什么出现，再讲是什么。
- 每个关键概念必须包含直觉、数学对象、shape、代码实现、失败模式。
- 不要写成术语表。
- 不要只给科普，要能指导本地实现和测试。
```

## 7. Codex 落地规则

拿到 Pro 输出后，Codex 不直接照抄，而是执行：

1. 提取优先级最高的改动。
2. 更新 `README.md` 和 `roadmap.md`，让项目定位先对齐。
3. 改当前章节正文，确保 problem chain 变深。
4. 改对应 `src/` 代码。
5. 改对应 `tests/`。
6. 运行验证：

```bash
pytest -q
ruff check .
python -m <module>
```

7. 如果验证失败，优先修本地实现；只有技术判断不清时再问 Pro。

## 8. 教材质量门槛

每章必须能回答：

1. 这章补上的能力是什么？
2. 这个能力的数学对象是什么？
3. 输入、输出、参数、loss 的 shape 是什么？
4. 最小实现在哪里？
5. 成功实验是什么？
6. 失败实验是什么？
7. tests 如何证明它没有坏？
8. 下一章为什么自然出现？

如果一章只回答“概念是什么”，就还不够专业。

## 9. 第 1 章专业样板要求

第 1 章不能只写 toy MLP。它应该成为后续所有章节的工程样板。

必须包含：

- 训练闭环。
- 计算图。
- 链式法则的局部直觉。
- 有限差分梯度检查。
- train/val split。
- overfit tiny 实验。
- 初始化。
- 学习率。
- batch size。
- 随机种子与可复现实验。
- `model.train()` vs `model.eval()`。
- `torch.no_grad()`。
- tests 不是 smoke test，而是学习验收。

代码至少包含：

- `TrainingConfig`
- `EpochMetrics`
- `HistoryItem`
- `TrainingHistory`
- `set_seed`
- `split_dataset`
- `make_dataloaders`
- `compute_grad_norm`
- `compute_update_norm`
- `train_one_epoch`
- `evaluate`
- `run_training`
- `run_overfit_tiny_experiment`

测试至少覆盖：

- dataset shape。
- forward shape。
- loss 明确下降。
- 参数确实更新。
- evaluate 不产生梯度。
- 固定 seed 可复现。
- 小样本可过拟合。
- train/eval dropout 行为不同。
- train/val split 无重叠。
- grad norm 和 update norm 大于 0。

## 10. 常见错误

### 错误 1：不给 Pro 当前内容

只说“帮我写专业点”会得到泛泛目录。必须发当前 README、roadmap、lesson、代码和测试。

### 错误 2：开太多 Pro 页面

Pro 页面太多会分散上下文，也浪费额度。一个任务保留一个完整上下文页。

### 错误 3：Pro 写完后 Codex 直接复制

Pro 的输出是编辑建议和素材，不是最终仓库状态。Codex 要负责整合、去重、验证。

### 错误 4：只写文章不写测试

本项目的教材目标是“能看懂、能运行、能修改、能复现”。没有测试的章节还不算完成。

### 错误 5：把等待超时当成失败

Chrome 工具调用超时不等于 Pro 停止。先重新读取页面状态，再决定下一步。

## 11. 每轮结束汇报格式

Codex 最后向用户汇报：

```text
已完成：
- 改了哪些文件
- Pro 给出的关键审稿意见是什么
- 我如何落地这些意见

验证：
- pytest -q 结果
- ruff check . 结果
- 示例脚本运行结果

下一步：
- 建议继续哪一章
- 需要 Pro 再审什么
```
